# Выполнить правку и подготовить merge

Применяй этот порядок в PRJCT-INDICv2 в пределах явно одобренной задачи. [AGENTS.md](../AGENTS.md) задаёт инварианты и разрешения. Новые глобальные настройки требуют отдельного согласования.

## Выбрать путь публикации

- Простую текстовую правку без изменения смысла, команд, контрактов или инструкций можно отправить прямо в `main`. Проверь diff и актуальный remote. Используй обычный fast-forward push. Не обходи защиту ветки.
- Код, зависимости, CI, конфигурацию и содержательную документацию проводи через PR. Формула, архитектура и инструкции агентов относятся к этому пути. Оцени риск по последствиям, а не числу строк.
- Разработку начинай в отдельной ветке `codex/`. Один PR должен решать одну задачу. Для последовательных задач используй связанные PR. В таком стеке target дочернего PR указывает на ветку родителя.

## Проверить и опубликовать результат

1. Сверь checkout, remote, ветку, scope и критерии приёмки. Для существенной работы обнови [актуальную задачу](../tasks/todo.md#active-task).
2. Выполни самые узкие достаточные проверки. Команды решения и условия повторного использования результатов даны в [инструкциях](../AGENTS.md#проверка) и [описании инструментов](tooling.md). Повторяй проверку при изменении её входов, дефекте или конкретной неопределённости.
3. Проверь staged diff и весь отправляемый диапазон commits. Включи только изменения задачи. После завершённой и проверенной реализации сделай commit и обычный push в ветку задачи. FAIL, UNKNOWN обязательной проверки или незавершённая ручная приёмка останавливают этот шаг.
4. Перед созданием PR проверь точные base/head, итоговый diff и отсутствие дубликата. Используй [шаблон](../.github/PULL_REQUEST_TEMPLATE.md). Завершённую работу открывай как ready PR. Для незавершённой работы используй draft.
5. Дождись CI на актуальных head и base. [CI](../.github/workflows/ci.yml) выполняет restore, format, build и tests. SKIPPED, PENDING и отсутствие запуска не означают PASS. После смены target проверь diff заново и получи новый CI для новой базы. Один retarget не доказывает запуск: текущий workflow не подписан на `edited`. Если нового запуска нет, закрой и сразу переоткрой PR для события `reopened`. Проверь его новый запуск и тестируемый merge commit.
6. Проверь review по следующему разделу. Основной агент проверяет каждое замечание по коду и требованиям. Исправь подтверждённые дефекты в том же PR. Для отклонённого замечания запиши причину.
7. Перечитай head/base после проверок. Сообщи SHA, CI, итог review, ограничения и следующий шаг. Для локального PASS отдельно укажи состояние удалённых проверок. При готовности к merge задай прямой вопрос о конкретном PR.

Merge выполняй только после отдельного явного согласия Стивена именно на этот merge. Разрешение на реализацию, push, PR или зелёный CI его не заменяет. Auto-merge не включай. После merge родителя перенаправь дочерний PR в нужную ветку и повтори проверку итогового diff и CI.

## Получить review

### CodeRabbit

CodeRabbit используй как обычного первого reviewer. Проверь автоматический запуск и прочитай итоговый отчёт, inline-комментарии и ответы. Зелёная отметка сама по себе не доказывает отсутствие замечаний. Свяжи результат с проверенным head SHA и diff.

Если review пропущен, установи причину. Проверь ready/draft, целевую ветку, настройки и сообщение бота. Затем один раз отправь `@coderabbitai review` либо используй **Trigger review**. **Autofix** и генерация тестов выполняют другие действия.

Повторный запрос нужен после нового head с непроверенными изменениями или установленного сбоя. `@coderabbitai full review` используй только для обоснованного пересмотра всего diff. Для неизменного diff переиспользуй применимый результат. Недоступный reviewer отмечай UNKNOWN или PENDING. Не отправляй бесконечные запросы и не меняй платный план автоматически. Два одинаковых сбоя требуют новой гипотезы.

CodeRabbit по умолчанию обнаруживает AGENTS.md и проектные Agent Skills. Не копируй инварианты в отдельный YAML без причины. Если вывод зависит от применения этих правил, проверь их фактическое использование в отчёте. Наличие файла этого не доказывает.

### Независимый чат для сложной работы

Для изменений формулы, архитектуры, live/replay parity, миграций, конкурентности или широких изменений проведи независимый review в новом отдельном чате. Не используй fork с историей автора. Reviewer работает только на чтение.

Передай точные base/head SHA, нейтральные требования, инварианты, команды проверки и пути к источникам. Не передавай вывод автора о правильности реализации. Используй существующий skill `code-review` с осями Standards и Spec. Для конкретного межмодульного риска добавь `blast-radius`. Если skill недоступен, укажи это и проверь требования и стандарты напрямую.

Основной агент проверяет результат и доказательства reviewer. Новый чат уменьшает влияние истории автора, но не гарантирует отсутствие ошибок. Проверяй этот сценарий на первой настоящей сложной задаче.

### Codex в GitHub

Для дополнительной проверки по необходимости используй комментарий `@codex review`. Сначала проверь подключение репозитория и доступ к Code Review. Подтверди реакцию и завершённый review на нужной версии. Если доступ не настроен, сообщи об этом. Не выдавай отсутствие ответа за PASS и не меняй настройки аккаунта автоматически.

Не запускай всех reviewer для каждой простой задачи. Учитывай область проверки Codex из текущей документации сервиса. На 2026-10-30 она указывает фокус на P0/P1. Отсутствие замечаний не доказывает полноту проверки.

## Учитывать защиту main

Соблюдай действующие правила GitHub. Процедура агента не является серверной защитой. Запрет force push и удаления совместим с прямым fast-forward push мелких текстовых правок. Обязательный PR для каждого обновления `main` закроет это исключение. Настройку защиты и её применение к администраторам согласуй отдельно. Не используй административный обход вместо выполнения проверок.
